# QuickJSEngine

[English](README.md) | **Русский**

**QuickJSEngine** — это легковесный JavaScript-движок для Qt, задуманный как аналог **QJSEngine** для консольных приложений или приложений на основе виджетов (QtWidgets), в которых не используется библиотека QtQml. Проект представляет собой удобную C++ обертку над современным движком [quickjs-ng](https://github.com/quickjs-ng/quickjs).

## Зачем нужен JavaScript в C++ коде?

Лично я использую JavaScript для добавления автоматизации в свои приложения. Пользователь может самостоятельно написать скрипт, который добавляет реакцию в программу на какое либо событие (я пишу программы мониторинга).

Когда-то для этого я использовал модуль **QtScript**, который основан на JavaScriptCore (движок WebKit), который давно не обновляется. Ему на смену пришел **QJSEngine** (движок V4), однако **QJSEngine** является неотъемлемой частью модуля QtQml. Использование **QJSEngine** тянет за собой зависимости QML, что избыточно для чисто консольных или виджет-приложений. **QuickJSEngine** решает эту проблему, предлагая независимый, быстрый и современный JavaScript движок.

## Основа: quickjs-ng

В качестве ядра используется **quickjs-ng** (ng - next generation) — форк оригинального QuickJS от Фабриса Беллара (Fabrice Bellard) и Чарли Гордона (Charlie Gordon), который активно развивается сообществом.
* Поддерживает современные стандарты JavaScript (ES2023+).
* Относительно компактный и очень быстрый интерпретатор.
* Движок **quickjs-ng** распространяется под лицензией [MIT](https://opensource.org/license/mit).

## Философия и отличия от QJSEngine

**QuickJSEngine** — это *легковесный* аналог, он **не стремится** реализовать абсолютно весь функционал **QJSEngine**, так как это несовместимо с концепцией легковесности. Весь функционал **QJSEngine** и не требуется, так как проект нацелен на консольные приложения, а не на графику в QML. Но все же движок стремится быть максимально близким к API **QJSEngine** для легкого перевода существующего кода.

**Что не реализовано (или реализовано иначе) по сравнению с QJSEngine:**
* **Политика владения объектами:** в **QJSEngine** GC (сборщик мусора) может удалить C++ объект. В QuickJSEngine C++ объекты никогда не удаляются сборщиком мусора JS: время жизни контролируется исключительно C++ кодом (через `parent` или `delete`), что безопаснее.
* **Q_GADGET:** передача структур Q_GADGET по значению не поддерживается. Используйте `QObject*` или `QVariantMap`.
* **Lossy `toVariant()`:** в режиме по умолчанию JS-специфичные типы (Map/Set/WeakMap/WeakSet/Promise/RegExp/DataView) и символы дают *невалидный* QVariant, тогда как QJSEngine даёт пустой `QVariantMap`, `QRegularExpression` или описательную строку. Для лосслесс-обёртки используйте `toVariant(RetainJSObjects)` в `QVariant<QQuickJSValue>`.
* **ES-модули:** `importModule()` / `registerModule()` следуют семантике QJSEngine; там, где QJSEngine отказывает, побеждает спецификация ECMAScript — циклические импорты, `import.meta`, top-level `await` и динамический `import()` работают (каждый из них — SyntaxError в QJSEngine).
* **Намеренно отсутствуют:** межевой слой V4 (`QJSManagedValue`, `QJSPrimitiveValue`, `coerceValue()`, `fromVariant()` — он повторяет модель памяти V4), конструкторы вида `QJSValue(42)` без движка (каждое значение привязано к своему движку — потокобезопасность по дизайну), `isVariant()` / `isUrl()` (deprecated с Qt 6.9 / V4-специфичные URL-объекты — Qt-типы-значения вроде QUrl, QPointF, QSizeF или QRectF конвертируются здесь в `undefined`, тогда как V4 оборачивает их в value-объекты; строки по-прежнему коэрцируются обратно в такие параметры там, где их принимает собственная QVariant-конверсия Qt), `uiLanguage()` (JS-переключение языка вне интересов консольных приложений).
* **Мелкие расхождения:** `newSymbol()` следует ECMA-262 (`description` установлен; V4 оставляет его undefined), `console.count()` ключует счётчики напечатанной меткой, а не скриптом и строкой, контекст перевода `qsTr()` фиксирован, а `Object.keys()` вызывает C++ геттеры (бросающий геттер валит перечисление), тогда как QJSEngine вообще не вызывает геттеры при перечислении ключей.

* **ES-модули, точный список:** `importModule()` / `registerModule()` реализованы с семантикой QJSEngine: singleton-кэш по каноническому пути, зарегистрированные модули матчатся голым спесификатором, default-экспорт = само зарегистрированное значение, снапшот enumerable own-свойств в момент регистрации, пути Qt-ресурсов `":/..."`, модуль, бросивший на верхнем уровне, при повторном импорте не исполняется заново. Сверх этого, каждое из перечисленного — SyntaxError в QJSEngine, но работает здесь: циклические импорты (разрешены по спецификации ECMAScript), `import.meta` (обычный объект по спецификации), top-level `await` (ES2022), динамический `import()` внутри скриптов `evaluate()` (и может запрашивать зарегистрированные модули), зарегистрированные имена без суффикса `.mjs`, голый спесификатор, не являющийся зарегистрированным модулем, — как файл относительно текущего рабочего каталога. Все ошибки загрузки модулей — объекты `SyntaxError`, как в QJSEngine, с нашими текстами сообщений (отсутствующий файл называется в сообщении вместо криптичного `Invalid null URL` у V4). `importModule()` по умолчанию прокручивает очередь микротасков (`setAutoProcessPromises(false)` отключает), поэтому модули с top-level `await` завершаются синхронно.
* **Доставка ошибок:** исключения JS-обработчиков сигналов репортятся (сигналом `uncaughtException` или `qWarning` без подписчиков), а эмиссия сигнала продолжается — как в QJSEngine; `Object.keys()` над QObject, чей C++ геттер бросает (через `throwError()`), падает с этой ошибкой, тогда как QJSEngine вообще не вызывает геттеры при перечислении ключей.
* **Необработанные реджекты промисов:** репортятся один раз, в конце тика, через тот же канал `uncaughtException` (семантика Node.js; у QJSEngine/V4 трекера реджектов нет вовсе). Реджект, закрытый поздним `.catch()` в том же тике, ретрактится и не репортится. Буфер ожидающих реджектов ограничен 1024 записями: при `setAutoProcessPromises(false)` и никогда не осушаемой очереди джобов он рос бы безгранично (каждая запись пинит промис и его причину в JS-куче — утечка, невидимая скрипту). После потолка САМАЯ СТАРАЯ буферизованная запись репортится немедленно, освобождая место, так что каждый реджект репортится ровно один раз — просто раньше конца тика для записей сверх потолка.
* **Отказы в lossy `toVariant()`:** в режиме по умолчанию (ConvertJSObjects) Map/Set/WeakMap/WeakSet/Promise/RegExp/DataView дают *невалидный* QVariant, тогда как QJSEngine даёт пустой `QVariantMap` (Map/Set/Promise) или `QRegularExpression` (RegExp). Символы тоже дают невалидный QVariant, тогда как QJSEngine даёт описательную строку `"Symbol(name)"`. Это осознанно: строкоподобный вариант молча бы конвертировался в metacall-конверсиях (например, nullptr записался бы в свойство `QObject*`) вместо бросания TypeError. Для лосслесс-обёртки используйте `toVariant(RetainJSObjects)` в `QVariant<QQuickJSValue>` (функции удерживаются в обоих режимах, как в Qt 6.12).
* **Отсоединённые буферы:** `toVariant()` отсоединённого `ArrayBuffer` (или TypedArray над ним) даёт пустой `QByteArray`, как QJSEngine. Вью за концом живого resizable `ArrayBuffer`, наоборот, валит конверсию — тоже паритет с V4; quickjs-ng бросает одинаковый `TypeError` в обоих случаях, поэтому буфер опрашивается через его геттер, чтобы их различить.
* **Конверсии даты/времени:** валидные `QDateTime`, `QDate` и `QTime` конвертируются в настоящий `Date` (эпоха в миллисекундах), невалидные — в Invalid Date (паритет V4). `QTime` заякорен ровно как в V4: Date — это ЛОКАЛЬНЫЙ `QDateTime(1971-04-01, время)` (выбранное qtdeclarative окно без DST-переходов для «времени без даты»), поэтому эпоха зависит от часового пояса, а `toVariant()` такого Date возвращает `QDateTime`, а не `QTime` — оба унаследованы от V4. Валидный `QDate` заякоривает UTC-полночь этой даты, ровно как V4 (`startOfDay(QTimeZone::utc())` в qv4dateobject.cpp), поэтому эпоха не зависит от часового пояса. Обратное направление тоже совпадает с V4: `Date` сужается к `QDate` через локальную дату с исключением QTBUG-92466 (инстант, являющийся ровно UTC-полночью дня, чьё локальное время попадает на предыдущие сутки — пояс с отрицательным офсетом, — даёт UTC-дату, поэтому строки-даты без времени и Date-якоря от QDate переживают раунд-трип), к `QTime` — через локальное время суток; невалидный (NaN) `Date` молча даёт невалидное значение цели — без TypeError — в любом слоте даты/времени.
* **Динамические свойства (расширение обёртки):** запись свойства, которое обёрнутый QObject не объявляет, создаёт C++ динамическое свойство на этом объекте (через `QObject::setProperty`). QJSEngine этого НЕ делает — он хранит неизвестные записи как обычные JS-свойства на объекте-обёртке, невидимые для C++ (проверено живым Qt 6.12); C++-видимое зеркало — осознанное расширение этой обёртки. `undefined` удаляет динамическое свойство (аналог JS-удаления свойства), `null` сохраняет QVariant-маркер нуля, читающийся обратно как JS `null`, а значение, вовсе не представимое как QVariant (Symbol, RegExp, Promise), бросает TypeError вместо молчаливого удаления свойства.
* **Запись `null`/`undefined` в свойства (паритет V4):** запись в мета-свойство коэрцирует JS `null`/`undefined` через ту же строгую таблицу, что и QJSEngine (проверено живым Qt 6.12), а не через JS-механику valueOf/ToNumber. `undefined` бросает `"Cannot assign [undefined] to <тип>"` для всех типов свойств, кроме свойства типа QVariant, которое принимает его как невалидный QVariant. `null` записывает нулевое значение типа там, где QJSEngine его принимает — null `QString`/`QByteArray`, `false` для bool, `0` для double/float, пустой `QStringList`, `nullptr` для `QObject*`, QVariant `std::nullptr_t` для свойства типа QVariant (читается обратно как JS `null`) — и бросает `"Cannot assign std::nullptr_t to <тип>"` во всех остальных случаях (целые, даты, QChar, контейнеры). Аргументы МЕТОДОВ, наоборот, следуют обычной JS-коэрции, как в V4: `null` даёт null `QString`/`QByteArray` (не строку `"null"`), `undefined` — строку `"undefined"`, числа — через ToNumber.
* **Proxy в `toVariant()` (паритет V4):** Proxy никогда не пробивается насквозь при конверсии в QVariant — `new Proxy([1,2,3], {}).toVariant()` даёт `QVariantMap` с индексными ключами (`{"0":1,...}`), а не список, в точности как QJSEngine (проверено). Это согласуется с `JS_IsArray` в quickjs-ng 0.18, который тоже больше не пробивает прокси.
* **Мёртвые обёртки QObject:** после удаления обёрнутого C++-объекта JS-обёртка выживает и `isQObject()` остаётся `true` (паритет с QJSEngine: классификация не ветвится на живость указателя), а `toQObject()` возвращает `nullptr`. Для QObject из чужого потока очистка по `destroyed` доставляется queued в поток движка; обёртка, закэшированная в этом окне доставки, перепроверяется по тождеству указателя при следующем `newQObject()` по тому же (возможно переиспользованному) адресу — переиспользование адреса не может подсунуть мёртвую обёртку вместо живого объекта.
* **`newSymbol()` и description:** QuickJSEngine следует ECMA-262 (`Symbol('x').description === 'x'`); у V4 `newSymbol()` оставляет description неопределённым, хотя `String()` по-прежнему печатает имя.
* **Ключи `console.count()`:** счётчики ключуются напечатанной меткой (семантика Node.js), а не скриптом и строкой, как в V4 — quickjs-ng не даёт C-коллбэкам информации о точке вызова. Печатаемый формат (`метка: N`) идентичен. Таблицы меток `console.count()` / `console.time()` ограничены 1024 записями: новая метка сверх потолка считается/таймируется, но не сохраняется (иначе таблицы росли бы неограниченно на динамических метках, а эта C++-память невидима для `memoryUsage()`); первое переполнение печатает однократное предупреждение.
* **Контекст `qsTr()`:** контекст перевода фиксирован (`"QQuickJSEngine"`); V4 выводит его из URL вызывающего скрипта, что недоступно C-коллбэкам quickjs-ng.
* **Кадры `exceptionStackTrace`:** разбираются из свойства `Error.stack` quickjs-ng в формат кадров V4 `функция:строка:столбец:файл`; нативные кадры несут `-1/-1` и пустой файл, как в V4. Брошенное не-Error значение (например, `throw 'str'`) даёт пустой список — quickjs-ng не прикрепляет к нему стек. Вложенный `evaluate()` из C++-слота сохраняет кадры внешнего скрипта в стеке внутренней ошибки — как в V4.
* **`isError()` для брошенных примитивов:** `isError()` истинно для ЛЮБОГО брошенного значения — `throw 42` возвращает error-помеченное значение, содержащее 42, — тогда как `isError()` у QJSEngine истинно только для Error-объектов. Это держит C++-обработку без ветвлений (всё, что `evaluate()`/`call()` репортит как ошибку, здесь и есть ошибка); `toString()` по-прежнему возвращает само значение. `errorType()` такого значения — `NoError`, в точности как в QJSEngine: класс несут только настоящие Error-объекты.
* **Ошибки, созданные движком:** `newErrorObject()` / `throwError()` строятся на встроенных прототипах и невосприимчивы к перезаписи скриптом `globalThis.TypeError` и компании (как в V4). Для `EvalError`/`URIError` глобальный конструктор всё ещё разыскивается: quickjs-ng 0.18 даёт C-хелперы только для остальных пяти классов. Сообщения со встроенным NUL сохраняются целиком (C-конструкторы `"%s"` останавливаются на первом NUL; полный текст восстанавливается обычной записью свойства). Стеки вызова, печатаемые `console.trace()`/`console.assert()`/`console.exception()`, строятся тем же способом (`JS_NewError()`) — подмена `globalThis.Error` не портит и вывод консоли.
* **Классификация `errorType()`:** класс определяется обходом прототипной цепи и сравнением указателей с встроенными прототипами ошибок, захваченными в конструкторе движка (до любого скрипта). Переписывание `e.name`, замена глобальных конструкторов после факта или сабклассинг (`class MyRE extends RangeError`) не меняют ответ — сабкласс репортит свой базовый класс. Расхождение: `Object.setPrototypeOf(err, RangeError.prototype)` переклассифицирует значение в `RangeError` здесь, тогда как V4 сохраняет класс, с которым объект был создан. Proxy-ловушка на пути обхода очищает pending-исключение и даёт `GenericError`. Обход останавливается после 16 прыжков по прототипам (защита от циклов); V4 обходит цепь до конца, поэтому класс, вплетённый глубже 16 звеньев, здесь читается как `GenericError`.
* **`errorType()` для Proxy:** Proxy вокруг Error сам не является Error-объектом (проверка по классу, как внутренняя проверка класса в V4), поэтому `errorType()` для него возвращает `NoError`.
* **Дефолтный `this` в `call()`:** опущенный thisObject привязывает глобальный объект движка, в том числе для strict-функций (паритет с QJSEngine). С явным примитивным thisObject примитив идёт по обычной JS-семантике вызова (sloppy-функция упаковывает его, strict — сохраняет). `callWithInstance()` для не-объектного instance привязывает глобальный объект — в точности как одноимённый метод QJSEngine: оба метода зеркалят свои Qt-аналоги.
* **Перерегистрация модулей:** повторный `registerModule()` с тем же именем заменяет модуль для новых импортов; предыдущая внутренняя запись модуля живёт до уничтожения движка (quickjs-ng держит def'ы модулей в списке рантайма без публичного API освобождения). Перерегистрация в цикле растит этот недостижимый список — избегайте неограниченных циклов перерегистрации.

**Дополнительные возможности API**

Поскольку QuickJSEngine создавался для консольных приложений, в него были добавлены функции управления производительностью и безопасностью, которых нет в QJSEngine:

* **Управление лимитами:** `setExecutionTimeoutMs()` (настенные часы, на прогон), `setStepBudget()` (детерминированный бюджет выполненных шагов движка на прогон — дополнение к таймауту для тестов: без таймеров, прогон под бюджетом всегда завершается, безостановочный цикл или регексп с катастрофическим бэктрекингом прерывается не позднее бюджета плюс один интервал опроса), `setMemoryLimit()`, `setMaxStackSize()`. Позволяют защититься от зловредных скриптов (DoS) и зависаний. Дефолты: куча JS ограничена 64 МиБ, бюджет JS-рекурсии — 512 КиБ плюс калиброванный допуск на C-машинерию, клэмпится к реальным границам стека потока движка; таймаут и шаг-бюджет по умолчанию выключены. Измеренный пол стека потока кэшируется на поток и не инвалидируется при переключении стеков: хостам с файберами/корутинами следует создавать движок на самом глубоком стеке, на котором движок когда-либо будет исполняться.
* **Управление кэшем байткода:** `setEvalCacheEnabled()`, `setEvalCacheLimit()`, `clearEvalCache()`. Позволяют тонко настроить потребление памяти при частых вызовах `evaluate()` с динамически генерируемыми строками.
* **Мониторинг:** `version()` (версия quickjs-ng), `memoryUsage()` (статистика памяти), `setGCThreshold()` (ручная настройка порога сборщика мусора).
* **Расширенный evaluate:** Поддержка передачи начального номера строки `evaluate(script, fileName, lineNumber)` для точной интеграции ошибок JS в логи C++.
* **BigInt:** Полная поддержка `BigInt` (конвертация в `qint64`/`quint64` и обратно без потери точности для чисел больше `2^53 - 1`).
* **QJSValue::engine():** Удалён ещё в Qt 5 и отсутствует в Qt 6, но он мне понадобился в многоскриптовом объекте для определения из какого скрипта запущена функция.

## ИИ инструменты

Весь код обертки разработан при помощи ИИ моделей, т.к. эта задача очень хорошо подходит для ИИ по следующим причинам:
1. Это всего лишь обертка к готовому существующему JavaScript движку, а не сам движок.
2. Результат работы обертки и альтернативного JavaScript движка можно сравнить с эталонным существующим движком и так быстро найти расхождения в работе.

Не думайте, что эта обертка была создана простым промптом типа сделай аналог **QJSEngine**. На самом деле это был достаточно длительный (полных ~10 дней) многоэтапный процесс поэтапного наращивания функциональности, тестирования регрессий, тестирования и улучшения производительности, code review и так по кругу много раз. Код писала модель **GLM-5.2/5.3**, code review проводили модели **ChatGPT**, **Claude Sonnet**, **Qwen**, **Kimi**, **DeepSeek**, **GLM-5.2**. Были места в коде, для которых я делал отдельные тестовые программы для выяснения реальной производительности разных подходов. Также я пользовался инструментом **Callgrind** для выявления горячих мест. 

Даже если вы пренебрежительно относитесь к ИИ коду, посмотрите хотя бы тесты производительности, там можно увидеть интересные моменты.

## Тесты производительности

Набор бенчмарков (02_speed) построен вокруг сценария встраивания: C++-приложение исполняет скрипты мониторинга, гоняет QObject'ы и QVariant'ы через мост, перевычисляет скрипты, создаёт и уничтожает движки. Взвешенный счёт поэтому измеряет «мост + смешанный скриптинг», а не «более быстрый JavaScript-движок»: в чистом вычислении JIT движка V4 сохраняет первенство на ряде задач (Math loop 1.20x, Object creation 2.03x и решительно RegExp 14.5x), тогда как интерпретатор берёт другие (Fibonacci 0.74x, вызовы функций 0.77x, JSON.parse 0.57x, строчные операции 0.48x). Производительность зависит и от архитектуры процессора: преимущество JIT растёт на быстрых ядрах с большими кэшами, интерпретатор масштабируется равномернее.

На Orange Pi Zero (не Zero 3) (ARMv7, 512 МБ RAM) QJSEngine не смог пройти тестовый набор (измерено на прежнем наборе из 24 кейсов): OOM-killer прибивает процесс на тесте Promise (движок держит ~420 МБ памяти, не освобождая её до пересоздания движка). QuickJSEngine прошёл весь набор с пиковым потреблением 88 МБ и нулевым удержанием памяти после сборки мусора.
